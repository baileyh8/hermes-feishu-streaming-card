# V5 建议：让任务更容易理解和操作

**状态：待决策的版本建议，尚未实施。** 依据 [2026-10-03 代码审查](reviews/2026-10-03-project-review.md)。本文不授权运行时修改、升级本机 Hermes、迁移用户配置或发布新版本。

## 建议方向

下一阶段围绕四件事：**看懂正在做什么、顺利完成交互、拿到完整结果、理解配置为什么这样生效。**

HFC 已有流式卡片、阅读预设、思考窗口、工具过程、审批续答、展示恢复与诊断。V5 的价值应是把这些能力组织成连贯体验，并补齐有效配置预览、信息归属和排障解释。建议沿用现有技术栈，随功能逐步整理代码。

## 先解决信息可信度

用户补充的“非 GPT 模型仍显示 GPT 周额度”是已复现问题，应作为下一轮修复候选，不能等到大改版才考虑。额度、模型、provider 和轮次必须有一致来源；没有证据时不显示别处的账户数字。当前本轮只完成审查和规则，**未交付该修复**。

同类规则适用于所有新体验：没有新事件不代表任务卡死，超时不是预计剩余时间，恢复卡片不代表任务继续执行。任何界面改版都必须保持这些事实边界。

## 推荐范围与实际增量

| 优先级 | 已有能力 | V5 增量 | 用户得到什么 |
| --- | --- | --- | --- |
| 核心 | 工具时间线、运行状态、后台等待的已观测输出 | 任务摘要：当前阶段/动作、最近一次有效更新、等待原因；无充分证据时明确未知 | 打开卡片即可判断现在需要做什么 |
| 核心 | approval/clarify、一次解析、续答卡与静态回执 | 统一交互布局与反馈：待决定内容、完整范围入口、提交中/已接收/失效状态清晰，移动端首屏可操作 | 减少漏选、重复点击和等待误判 |

## 三个核心工作包

### A. 任务摘要与等待解释

典型场景：任务正在跑命令，卡片停留几十秒，用户无法判断是在等待、没有新输出，还是需要输入。

- 用现有事件构建独立展示模型：当前状态、最新动作、最后观测时间、当前需要用户处理的事项。
- 阶段仅来自可验证事件或明确映射；无结构化阶段时显示已有动作。不上第二个 LLM 生成未经核实的进度。
- 等待卡片区分“等待你的选择”“已观测到进程仍运行”“最近没有新状态”“连接重建，待同步”。
- 默认压缩已成功的过程，失败、权限请求与最新动作优先可见；保留完整结果和已有显式阅读设置。
- 沿用 flush 与终态顺序，不为动画增设独立消息，不绕过 Card JSON 预算。

验收样例：同一回放轨迹分别包含长工具、空闲、断连重建和失败；卡片不能虚构完成、百分比或 ETA，终态后不继续动画，消息数量不增加。

### B. 交互操作与续答体验

典型场景：手机上审批正文很长，按钮离首屏远；用户点过一次却不知道有没有提交成功。

- 在安全范围完整可达的前提下，优先呈现待决定事项与操作；具体布局先验证 Feishu JSON 方言和移动端能力。
- 提交中、已接收、已过期、提交失败有一致反馈；重复请求复用同一结果，不重复执行。
- 复用原 Hermes request/handle。旧卡失效只能引导重新发起请求，或使用已有、可证明存活的审阅恢复路径；不能复活旧 token。
- 审批结果与后续答案关联明确；不把静态回执误画成仍等待中的表单。

验收样例：桌面、Android、iOS 分别完成一次多选/输入与审批，覆盖长范围、网络失败、双击、过期和重启。截图证明布局，实际执行证据证明一次选择只解析一次。

### C. 有效配置解释与预览

典型场景：用户选了 focused，又改了 profile 或 bot 的宽度，不清楚最后谁覆盖了谁。

- 第一阶段仅做只读解释与样例预览，复用真实配置合并代码，不能维护另一份容易漂移的规则。
- 覆盖阅读、宽度、字号和页脚；显示 default/global/profile/bot 的来源及显式重置。
- 清楚区分“按此文件下次加载的结果”和“当前运行进程已确认加载的结果”；没有运行证据时不写已生效。
- 在已接通 Hermes/飞书的安装上引导新用户选预设，展示预期变化、权限需求和是否要重启。
- 如后续加入写配置功能，再单独实现作用域确认、差异预览、原子写、备份与回退。只读入口不隐式启动 repair/update。

验收样例：同一字段在全局/profile/bot 中覆盖与重置，预览结果与实际 renderer 一致；`width_mode` 在解释中可见；私密路径、账号和 route ID 不进入群卡片。

## 后续增强的边界

结果回看应先复用本地私有、有界检查点和已存在的飞书消息；若提供跳转，必须有平台支持的真实目标。它不自动形成永久聊天档案。普通卡片和 CardKit entity 的重启能力分别设计、验证，不能互相借用承诺。

诊断报告采用字段白名单，先本地预览脱敏内容，再由用户选择导出；不默认上传日志、正文、配置文件或检查点。建议动作与实际执行分开，不能把“检查一下”解释为重装或升级。

## 技术栈与代码演进

| 主题 | 推荐取舍 | 进入实现前的条件 |
| --- | --- | --- |
| Runtime | 保持 Python + asyncio/aiohttp sidecar | 没有必要重写为另一语言或 Web 平台 |
| Python | 评估 V5 最低 3.11，默认开发 3.12 | 发布旧环境检测、迁移/回退说明，先跑支持矩阵 |
| 配置/协议 | 继续 PyYAML、dataclass 与边界验证 | 新字段定义默认、优先级、作用域与兼容性；不为表单单独引入复杂框架 |
| 状态 | 保持有界内存/私有文件 | schema、TTL、容量、损坏处理和降级行为明确；没有新需求就不引入数据库/队列 |
| 集成 | 已验证的 Hermes native 能力优先，缺口保留精确兼容路径 | 每项减少补丁的决定有 call-site 和真实 subprocess 证据 |
| 代码组织 | 先提取展示模型，再分离事件适配、状态决策与 I/O | 提取前固定事件轨迹结果，不同时改变协议、默认值和投递语义 |
| 开发工具 | 有限目录试用 lint 与边界类型检查 | 独立变更、增量门禁；不混入全仓格式重排 |
| 测试 | 快速相关组 + 全量/上游固定矩阵 + 多端验收 | 修好 preflight 覆盖说明与上游 fixture 入口，报告所有 skip |

当前 HFC 仍声明 Python >=3.9。上述 floor 是建议，不能提前当作已变更。Python 3.9/3.10 已结束官方支持，而今天读取的 Hermes main 声明 >=3.11,<3.15，因此建议收敛支持范围；3.13/3.14 必须完成全部适用路径测试后再宣称正式支持。[Python 生命周期](https://devguide.python.org/versions/)、[Hermes 依赖声明](https://github.com/NousResearch/hermes-agent/blob/c8301ea6c9b797184df16a9c5dd462400b264ff4/pyproject.toml)

Hermes 官方已有 plugin 扩展点，支持以能力验证为基础逐步减少侵入；官方说明不等于某个 hook 的参数、时序与 HFC 当前契约已经一致。[Hermes plugin 文档](https://hermes-agent.nousresearch.com/docs/developer-guide/plugins/)

## 方案比较

以下是工程判断的默认权重，**不是用户调研或实测结果**。分数 1–5 越高越好；交付成本列表示越容易交付分越高。安全和正确性属于必须通过的门禁，不参与加权抵消。

| 方案 | 功能价值 35% | 体验收益 30% | 交付可控性 20% | 兼容可控性 15% | 加权值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 小规模显示修补 | 3 | 3 | 5 | 5 | 3.70 |
| **任务体验升级，保持 sidecar** | **5** | **5** | **3** | **4** | **4.45** |
| 重写成通用任务平台 | 4 | 3 | 1 | 1 | 2.65 |

推荐第二项，与本次“功能升级与体验优化”的目标最一致。若近期资源仅够维护兼容性，则先交付小修和只读配置解释，缩小版本范围；不要为保住“大版本”名称强行做破坏性迁移。

## 实施顺序与完成门槛

| 阶段 | 产物 | 进入下一阶段的条件 |
| --- | --- | --- |
| 0 · 范围确定 | 确认核心工作包、已知问题清单、Hermes stable/main SHA、当前 UX/性能基线 | 方案被选定；不把本报告视为实现授权 |
| 1 · 基础与试验 | Python 迁移设计、测试入口改进、展示模型与交互样稿 | 关键风险有证据，旧轨迹与配置结果保持 |
| 2 · 核心体验 | A/B/C 三项逐步交付；读写配置分阶段 | 功能回归通过，小范围用户反馈可追溯 |
| 3 · 候选验收 | 普通 wheel/公开安装来源、多端使用、升级和回退记录 | 全量与精确上游矩阵通过，未解决边界写清 |

不在未估算开发容量和 Feishu 客户端验证成本前承诺日期。功能可以分批进入 4.x；只有明确的 Python floor 或配置/协议破坏性迁移才需要相应 major 语义。

## 验收目标：先测基线，再承诺改进

以下为建议目标，尚未测得：

- **新用户理解与设置：** 选择约 5 名首次使用 HFC 的用户试用；在 Hermes 和飞书机器人已接通的前提下，10 分钟内完成预设选择并解释当前状态。飞书应用审批和账号开通不计入这项时间。样本用于发现问题，不作统计显著性声明。
- **交互：** 桌面、Android、iOS 分别验证首屏可发现操作、完整授权范围可达、一次点击有回执；不能以桌面结果代替手机。
- **正确性：** 场景矩阵内零重复执行、零跨用户改卡、零虚假完成；完整答案可交付，非相关模型不出现 Codex 额度。
- **性能：** 在同硬件、同事件轨迹与同模拟外部延迟下测 p50/p95、峰值内存和 PATCH 次数；候选目标为关键路径 p95 不比基线劣化超过 10%。外部 Feishu API 时延单列，不归因于 renderer。
- **成本与容量：** 每轮消息数不因装饰性状态增加，检查点/缓存/重试有上限，最终组合 payload 通过项目共享 serializer 的预算检查。
- **迁移：** 旧显式配置不丢失，拒绝不支持的 Python 时给出明确动作，失败保持原状态，降级限制有实际验证。

原始证据与最终结论分开记录；测试数、HTTP 200、设计稿和 mock 回调都不能单独作为产品体验完成的证明。

## 本版不建议纳入

重品牌、通用管理后台、多平台大一统、第二套 agent/调度/审批系统、独立模型调用、无人值守执行恢复和永久任务档案。这些会显著扩大产品边界，应在有明确需求和维护容量后单独评估。
