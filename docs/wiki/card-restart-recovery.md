# 卡片连接恢复与执行恢复

HFC 只恢复展示和投递身份。Hermes 仍是执行任务、会话归属、启动续跑和授权的唯一负责人。

## 私有卡片检查点

独立 runner 在私有 state directory 下启用 `card-checkpoints-v1`。每个已发送的普通会话卡保存有界 JSON 检查点：原 Feishu message ID、profile/bot、应用身份摘要、会话正文和时间线、顺序号、回复位置。文件采用原子替换，目录 0700、文件 0600；拒绝符号链接和非当前用户文件，记录有摘要校验，最多 128 条、每条 1 MiB、保留 24 小时。包含对话正文，应按本地 Hermes 会话资料保护，不复制到公开日志或诊断附件。

不保存或恢复审批 token、运行中 waiter、callback、native admission 和执行栈。原来等待授权的卡片恢复为失效状态，用户必须重新发起请求。Native handoff 继续使用既有独立账本，不混入会话检查点。

开发分支补齐独立交互卡的展示恢复：检查点最多附带一份对应辅助消息的静态回执，保留实际消息 ID、原卡方言和经脱敏的完整审阅内容；待选或暂停状态预先转成无按钮的失效展示。该记录继续受整份检查点的容量、保留期和 profile/bot/应用身份校验约束，不包含授权 token，也不会恢复 waiter。旧检查点没有辅助消息身份时不猜测历史消息，因此不能追溯刷新这类旧辅助卡。

正常交互过期同样更新实际辅助卡。只有完整独立回执得到明确 PATCH 成功确认后，原 owner 才移除重复的审批范围；容量不足或更新失败时保留原来的范围。终态正文先投递，辅助回执不能阻塞终态 ACK 和答案。上述开发分支行为的实际验收见[任务卡片验收记录](../reviews/2026-10-03-task-cards-acceptance.md)。

若首条事件就是交互，原卡可能使用 legacy callback 方言。检查点仅保留经既有 renderer 脱敏的静态问题/选择文本，不保存按钮或 token；恢复提示及续答创建失败的正文回退都沿用该卡原方言。新续答确认发送后改由 schema 2 卡承载正文，静态回执仍留在原消息中。实际组合后的 Card JSON 再次经过容量检查，不能为保留回执而截断答案或越过平台限制。

未使用续答段或 legacy owner 的普通卡检查点省略新增空字段，可由 v4.6.3 读取。已经记录新展示段或静态交互 owner 的检查点需要新版读取；回滚 v4.6.3 会跳过这些新记录，不承诺继续更新其原卡。降级前应让运行中的轮次结束并保留当前版本私有检查点备份；已有飞书消息不会因此删除，也不会恢复旧审批执行。

重启加载只接受当前投递策略仍允许、profile/bot 绑定和 Feishu 应用身份未改变的记录。继续沿用原 message ID；同轮终局更新原卡，重复终局不另发卡。非终态卡先静态提示连接已重建、等待执行状态同步，避免在没有进程状态证据时永久显示动画或假称任务成功。收到原轮有效事件后继续正常更新。跨 chat/profile、未知身份和损坏记录不能用于恢复。

记录写入失败不改变已经发生的投递、不再发第二条消息；health diagnostics 的 `card_checkpoint_state` 标记 unavailable。它意味着该实例没有可靠的重启恢复能力，不能把发送成功等同于检查点成功。达到容量上限不驱逐尚在保留期的旧卡记录；新增记录停止保存并报告 unavailable。

这一机制不能追溯恢复升级前没有检查点的卡片，也不承诺平台发送成功与本地原子写之间崩溃窗口的永久 exactly-once。

## 启动恢复与传输重试

已完成的回合在同一消息上重开时，HFC 在建卡前保存本次投递身份、回复位置和待确认正文。飞书建卡回执丢失后，支持 UUID 去重的消息可在有效期内沿用同一 UUID 找回。HFC 拿到卡片 ID 并确认当前正文已写入后才接管终局。CardKit 建卡结果不明、去重期限已过或终局写入无法确认时，正文交还 Hermes；飞书已接受的占位卡可能仍然可见。

如果找回主卡时收到的就是终局，HFC 确认正文后会按本轮设置发送完成提醒。提醒使用原话题位置，发送后写入检查点。再次重放同一终局时，已记录送达的提醒不会重发。

同一群话题里，两个人可以引用同一条消息。旧版事件只有租户用户 ID 时，新检查点会保存绑定到原卡的请求人摘要。重启后，HFC 用事件中的用户 ID 复算摘要，匹配后才凭这条引用更新原卡。摘要只供展示路由使用。旧检查点缺少摘要时，仍须有其他证据才能确定请求人。

对使用旧引用投递的终局，事件指纹用来识别同一次重试。检查点另行记录飞书是否确认写入。若重启发生在更新原卡期间，可继续更新原卡。若补发已经开始但结果未知，只有在同一投递位置且 UUID 仍有效时才重试补发。过期后保留 `unknown`，避免再次建卡。HTTP 的 `applied` 表示 HFC 已接管该事件，核对正文送达要看飞书写入结果。

旧版检查点可能只有引用关系，缺少终局事件指纹。重启后，如果 HFC 无法判明收到的是旧终局重放还是新回合，会保留 Hermes 的原生正文投递。此时可能出现重复文本。较新的终局或有独立身份的新回合仍可开卡。

旧版 Hermes 有时会复用上一轮消息 ID，直接发送新回合的完成或失败事件。若事件带有 `policy_new_turn=true`，且时间晚于上一轮，HFC 会按本轮配置投递正文，保留上一轮的卡片。选择原生方式投递长答后，下一轮短答仍可正常开卡。

两轮之间没有开始事件或流式片段时，旧版完成 hook 会核对 Hermes 事件的 generation 和时间。能确认是后一轮时，hook 才补上新回合标记。事件顺序无法确定时，Hermes 仍可投递正文。

旧版终局带有新回合标记或可核实的 generation 时，飞书确认整份正文送达后，展示检查点会保留事件指纹和确认时间。这适用于直接建卡、更新已有卡片，以及确认送达的补发或完整分段。同一位置最多保留最近 16 条，从各自确认送达起算一小时。重启后，原事件在这个窗口内精确重放，即使期间已有下一轮卡片，也能取回送达回执。同一完成钩子重试时沿用首发耗时和输出速率；正文、附件或路由变化仍会改变指纹。续卡只送出一部分或写入结果仍为 `unknown` 时，该终局不会获得这条回执。后续交由 Hermes 原生投递时，检查点可以只保留已确认的历史收据及路由，供重放和下一次确认建卡使用。

如果长答已经建了首卡，但续卡发送失败，原生回复会承载完整长答。后续明确属于新回合的短答使用自己的建卡 UUID。即使 sidecar 在两轮之间重启，或者短答建卡时丢失确认，重试也会沿用短答的 UUID。带签收凭据的原生交接仍按原交接记录处理。

若占位卡已经发出，但检查点写入失败，重启后的 sidecar 可能找不到原卡。此时聊天终局用该事件的指纹生成独立的建卡 UUID，即使 Hermes 省略新回合标记，也能把正文送到新卡。原占位卡可能仍在群里。相同终局重试复用同一 UUID。如果旧版本已发出建卡请求、回执丢失且没有可用的检查点，跨版本重投可能多出一张卡。升级前宜先等正在投递的回合结束。

只对签名形状已知的 Hermes `_run_startup_resume_event(self, adapter, event, session_key)` 加有限 sidecar policy 可用性等待。未知签名不包装；非 Feishu、禁用插件、明确 native 策略和 HTTP 拒绝不强行等待卡片。原 Hermes handler 仍只调用一次；等待不能恢复授权或绕过会话 ownership。

terminal 传输的 75 秒预算包括请求和同轮发送锁等待，退避后重新检查剩余时间。重试复用原事件身份，HTTP 4xx 不重试；日志只保留重试次数和异常类，排除原始消息 ID、URL、异常正文。网络超时并不证明服务端未处理，所以服务端幂等和检查点同样必要。

## 验证

`tests/integration/test_combined_stability.py` 覆盖真实本机 HTTP 的重建 app、同卡终局、重复投递、错误 chat、旧审批失效、磁盘失败和启动等待；`tests/unit/test_session_store.py` 覆盖权限、损坏、保留时限和符号链接。模拟 Feishu 客户端不能替代真机视觉验收。
