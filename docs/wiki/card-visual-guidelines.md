# 卡片视觉体验规范

**本页是卡片体验改动的发布门槛。** 开发分支的可选 `task` 布局正在真实客户端验收，尚未通过全部门禁。具体用法见[任务卡片](../task-cards.md)，功能边界见[功能规则](feature-rules.md)。

2026-10-03 的真实长工具任务暴露了阻断问题：标题、工具区、页脚重复显示执行状态与动作，参数进一步挤占首屏。Bailey 要求同时提高布局逻辑、美观、整洁、字号、颜色、间距及信息密度的标准。此次失败作为负面样本保留；本地预览或自动化通过不能覆盖它。

## 设计目标与现有基础

卡片应让用户快速看懂状态、阅读答案、找到操作，长时间阅读也不疲劳。视觉质量本身是版本交付目标，不能仅以“功能可用”验收。

每种状态只设一个主要阅读重点，其他信息为它服务。验收必须回答“为什么放在这里、为什么用这个字号和颜色、是否值得占据首屏”。没有作用的标签、装饰、分隔线和空白应移除；有用的内容通过合适的布局保留。

## 阻断发布的条件

下列任意一项不满足，视觉验收即为失败，不用测试数量、平均评分或“平台接口成功”抵消：

- **阅读逻辑：** 首屏能识别任务状态、主要内容和是否需要操作。待审批的完整问题、范围与按钮保持关联；完成卡首先呈现结果。无需逐段查找才能理解当前发生了什么。
- **信息去重：** 折叠区外，任务状态只出现一次，当前动作只有一个主要展示位置。工具序号、全局工具计数和累计耗时有各自用途；不得在标题、正文、页脚机械重复。展开后的历史允许复述，但必须明确属于过程记录。
- **布局完整：** 实际客户端上没有非预期裁切、重叠、溢出、按钮不可达、表单错位或异常大空洞。最终答案、失败原因和授权范围完整可达；禁止缩小文字或删掉内容来制造整洁。
- **字号层级：** 正文为主要阅读字号；过程与统计降低一级。默认 `task` 使用正文/通知 `normal`、过程 `small`、统计 `notation`，同类内容一致；不把小字号扩散到主答案，不在一张卡上混用无必要的字号等级。长路径、中英文、代码、表格和放大字号都需实测。
- **颜色节制：** 单个状态使用一个主强调色，其他内容以中性文字为主。蓝色用于运行，橙色用于待处理，绿色用于成功，红色用于失败，中性色用于未知；文字也说明含义。模型名和统计不借品牌色抢注意力。浅色与深色均须可读，不能依靠低对比灰字实现“轻量”。
- **间距与对齐：** 同级区域的边距、行间距和对齐一致，区块间距大于同组内容间距。正文、当前动作、过程入口、操作区和统计有清楚分组。分隔线只分隔真实层级；空统计不留分隔线，短答案不套空面板或堆叠横幅。
- **信息密度：** 短答紧凑，长文有段落和阅读节奏。运行卡首屏以当前动作及必要上下文为主；原始参数和成功历史默认进入过程区。只有确认参数已进入实际渲染的过程区才可从正文移除；过程被关闭或容量限制省略该工具时保留可见入口/内容。不得把整张卡做成日志墙。
- **交互清晰：** 按钮名称能预判结果，批准与拒绝同样容易发现。长标签自然换行，完整范围可查看；输入、选中态与焦点不被更新清空。手机实际点击、多选、输入和提交必须成功，截图不能代替操作。
- **动态稳定：** 比较开始、运行中、静默、提交前后和终态的连续画面。计时或动画不能反复撑开区域、抢走阅读位置或重置折叠。静默和恢复不能虚构正在执行，终态不继续动画，不为装饰新增消息。
- **证据完整：** 桌面、Android、iOS 分别提供本轮版本的实际操作结果与视觉记录。缺少客户端、主题或关键状态证据时记录为未验证；浏览器窄屏、离线 HTML 和旧版截图不能补位。发布依赖的缺口必须补齐，或由 Bailey 明确缩小发布范围。

这些要求适用于本轮默认任务布局及其明确支持的设置。旧预设和用户显式配置继续兼容；不能用默认布局的整洁要求擅自删除用户主动保留的信息。

## 每轮视觉验收如何执行

1. 固定合成内容与执行脚本，记录 HFC commit/wheel、Hermes SHA、客户端版本、操作系统、主题、窗口/屏幕宽度、系统/客户端字号和阅读预设；不用私人聊天作为样本。
2. 用相同内容比较基线与候选，逐状态审查布局顺序、重点、字号、颜色、留白与密度；给出具体差异，不能只写“更美观”。对短答、长文和交互分别判定，不能一张最好看的完成卡代表全流程。
3. 桌面至少检查常用宽度与约 420 px 的窄聊天区域；手机记录实际可用宽度，检查系统默认字号和一档放大字号。客户端不支持某种条件时记录限制，不把模拟视口写成真机。
4. 在支持的客户端检查浅色/深色。展开过程、滚动长文与表格、阅读代码、切换折叠、操作按钮和填写多选/自定义输入；保留提交前后和终态的对应证据。
5. 快速浏览首屏，指出状态、主要内容和下一步。若仍需解释才能理解，回到布局修订。没有用户试用记录时不得声称达到“5 秒理解”等量化收益。
6. 按上面的每一项给出通过、失败或未验证及证据。先修阻断项，再重拍受影响状态、重做相关交互并跑回归。复测新的实际产物，不能沿用修复前截图。

验收报告同时列出信息逻辑和视觉质量结论。只证明没有溢出、按钮能点、颜色字段合法，不足以证明美观和整洁；仍需核对主次是否清楚、分组是否自然、颜色是否克制、间距是否一致、密度是否适合该状态。

当前 renderer 已有状态标题/副标题、思考和工具面板、交互卡与页脚；配置支持 body/reasoning/tool/notice/footer 字号角色、阅读预设及普通 JSON 2.0 卡片的宽度模式。改版应整理这些已有能力，而非重复增加一组外观开关。默认值和用户显式选择的变动要有迁移说明。

## 视觉规则

| 维度 | 设计要求 | 验收重点 |
| --- | --- | --- |
| 信息层级 | 主要视线落在当前需要理解的内容：运行时看动作，待输入时看问题与操作，完成后看结果；过程与统计退居次要 | 用户能区分状态、正文、操作、过程和统计 |
| 字号与行文 | 正文清晰易读，标题简短；思考/工具与正文视觉区分，页脚克制；同类角色保持一致 | 中英文、长路径、代码、多行文字不挤压；不能为塞内容一味缩小字号 |
| 留白与对齐 | 同类区域使用一致间距和对齐；优先通过分组、留白建立结构，适量使用分隔线 | 没有无意义大空洞、密集标签墙或层层面板；短答与长答均自然 |
| 颜色与图标 | 颜色表达状态，文字同时说明含义；品牌/模型标识不抢过答案；图标有固定含义 | 不能只凭红绿判断结果；浅色与深色主题分别检查对比度 |
| 阅读密度 | 首屏保留主要信息；成功过程可折叠，失败和需处理事项容易发现；长内容分组但不丢失 | 完整答案与授权范围可达，不用静默截断换整洁 |
| 按钮与表单 | 操作标签明确、分组一致、便于手机触达；审批的批准与拒绝同等可发现，不用配色诱导批准 | 长选项自然换行；提交反馈清晰，输入不被刷新抹掉 |
| 页脚与统计 | 保留有依据且与本轮相关的数据，弱化其视觉权重；额度必须与模型/provider 匹配 | 不出现无意义 Unknown/零值堆叠或非 GPT 卡片的 GPT 周额度 |
| 动态稳定性 | 运行变化不造成无谓的高度跳动、反复折叠或输入失焦；终态停止动画 | 相邻流式帧可比较，阅读位置稳定，PATCH 与消息数量有界 |

工具自己的失败结果与任务整体状态可能不同，应保留这种必要区别；这不构成三处重复同一个“执行中”的理由。

交互转交同样必须区分展示状态与执行状态。旧卡转为静态记录后，不能保留“执行中”、旋转图标或伪造“已中断”；转交说明只出现一次。多选下拉项应包含可识别的文字，长选项允许保留有意义的短预览，但完整选项必须仍可查阅，提交值不得随显示文字改变。选择回执用自身的已记录/失效状态配色，不继承尚未结束的任务颜色。

中性色以客户端实际效果为准。真实浅色桌面中 `grey` 标题呈现灰底白字，不能因枚举名是灰色就视为低强调、足够清晰。未知与转交状态使用官方标题组件支持的 `default` 模板，并继续复验主题对比度；枚举与平台边界见[飞书标题组件](https://open.feishu.cn/document/feishu-cards/card-json-v2-components/content-components/title)。

## 状态对应的阅读重点

| 状态 | 最先看见 | 次要内容 | 必须避免 |
| --- | --- | --- | --- |
| 运行中 / 长等待 | 当前状态、已观测动作、必要的等待解释 | 思考、已完成工具、累计统计 | 堆叠多个同义“执行中”、装饰性刷屏、假进度 |
| 待审批 / 待选择 | 完整问题、授权范围与清楚的操作关系 | 已执行过程和统计 | 只在可能省略的长标题中放关键信息；操作脱离风险范围 |
| 已完成 | 最终答案与结果入口 | 完成标识、可回看的过程、统计 | 状态横幅或工具历史占据答案之前的大量空间 |
| 失败 / 中断 | 发生了什么、保留下来的结果、可用下一步 | 相关失败过程与诊断细节 | 只有红色没有解释；把保留正文误当成功 |
| 连接恢复 / 状态未知 | 正在等待执行状态同步及可确认事实 | 原展示内容与必要说明 | 恢复动画让用户误以为任务已续跑 |
| 独立通知 | 事件摘要与确有必要的操作 | 可选细节 | 无关模型、额度和工具统计 |

该表定义阅读优先级，不要求所有状态套用完全相同的组件顺序。审批范围与完整内容的安全约束优先。

## 内容和客户端边界

- 长答案、表格、代码、链接、附件和多选输入分别设计；折叠摘要不能代替完整正文，表格不能为了窄屏删除重要列。
- 宽度、换行、留白、字号和组件状态只使用对应 Feishu/Lark 方言确认支持的能力；设计稿不能假设可任意注入 CSS、字体、断点或粘性按钮。
- 普通 JSON 2.0、legacy 交互卡和 CardKit streaming 分别验证；允许平台限制下的合理差异，但状态含义与阅读层级保持一致。
- 桌面、Android、iOS 分别检查窄窗口、长内容、触达和输入；在客户端支持时检查浅色/深色主题与放大字号。不能从缺少可靠来源的字段推断“手机模式”。
- 可访问性检查包括颜色以外的状态提示、对比度、文本可读性、焦点与读屏顺序；后两项需实际客户端操作，截图不能证明通过。
- 视觉改版不增加第二套状态来源，不改变 authorization、owner、终态或投递顺序；最终组合卡片继续通过共享容量检查。

## 先设计，再实现

以下方案比较与方向确认适用于新的整体改版。已获授权的实现与验收修复继续按已确认方向推进，不因例行复测重复请求设计确认。

1. **基线：** 在指定 HFC/Hermes 版本采集脱敏的真实卡片，注明客户端、系统、主题、窗口宽度、字号和阅读预设；明确哪张图对应哪个状态。
2. **候选：** 用相同内容制作至少两种可实现方向，例如“正文优先、过程轻量”和“任务分区、状态明确”；比较信息层级、密度与操作位置，而非只换颜色。
3. **确认：** 提供桌面与手机主要状态的对比样稿、组件规则及平台限制，待 Bailey 确认视觉方向后再修改 renderer。
4. **实现后复测：** 用同一内容与条件重拍截图并执行交互，验证设计与真实卡片相符；AI 概念图、本地预览和真实 Feishu/Lark 卡片分别标注。

只读审查不构成实现授权；取得实施与真实验收授权后执行上述流程。验收暴露的问题先修复，再重新通过对应门禁。

## 验收样本与建议目标

样本至少包含：短答案、长 Markdown/表格/代码、长工具等待、多工具/思考、长审批范围、多选输入、失败/中断、连接恢复、独立通知。各模板使用脱敏固定内容，避免样稿靠删减内容显得更整洁。

| 项目 | 建议目标或判定方法 |
| --- | --- |
| 首屏理解 | 用户约 5 秒内能指出当前状态及下一步是否需要操作；这是待试用验证的目标 |
| 结果阅读 | 完成卡的正文成为主要内容，能迅速定位结论；与同内容基线比较 |
| 布局 | 目标客户端上无非预期裁切、重叠、不可达按钮；字号放大后仍可用 |
| 稳定性 | 流式更新不清空输入、不反复重排固定区域；终态没有持续动画 |
| 信息完整 | 最终答案、授权范围和必要失败信息完整；无无关额度或假状态 |
| 成本 | 改版不靠额外消息或显著增加 PATCH 实现装饰效果；记录卡片体积和更新次数 |

量化收益仍需实测，不因制定标准就宣称已经达到。验收包需包含逐状态截图、客户端条件、设计差异、自动化结果、实际操作结果、失败与复测记录，以及未覆盖项。
