# 稳定性测试与发版准入

测试数量和行覆盖率不能单独证明稳定性。每个缺陷必须对应可复现的用户流程、错误结果和回归断言；未知根因不得因相邻修复而关闭。

## 缺陷修复规则

1. 记录 Issue、Hermes/HFC 版本、触发步骤、期望与实际结果；使用脱敏数据。
2. 优先写能在修复前失败的测试，保存失败原因；无法复现时明确标记待验证。
3. 测试用户可观察的结果：卡片终态、正文、消息数量、Topic 位置、一次点击的实际执行、账本最终状态。仅检查 marker、HTTP 200、进程存活或 mock 被调用不算流程通过。
4. 同时验证正常、失败、重复/晚到以及恢复路径。未知接口或来源漂移必须拒绝安装；不得放松 integrity fence 换取测试通过。
5. 变更后跑相关矩阵；候选提交上跑全量及 diff 检查。缺 fixture、超时、依赖缺失、环境差异都必须逐项归因，不能把失败列为“预期绿灯”。
6. 合并后在精确 merge SHA 验证；生产/真机使用普通 wheel，记录版本和实际导入位置。editable 安装与模拟客户端不得冒充公开安装验收。

## 必测场景

| 风险 | 自动化证据 | 真实边界验收 |
| --- | --- | --- |
| Hermes 升级与安装 | 支持源码的 apply/remove 逐字往返、幂等；签名/参数/控制流漂移拒绝；record → hook → send → finalize 实际执行及失败结果 | 固定 Hermes SHA 的新装、升级、恢复，重新启动后 fence 不反复出现 |
| 失败误报完成 | failed/interrupted/partial/completed=false；保留正文；无成功通知；晚到事件不翻转终态 | 真实 provider 失败卡片与 Gateway 结果一致 |
| 打断与新轮 | 旧卡结束但不宣告成功，保留部分文本；新卡继续；不同 Topic/profile 隔离；延迟 PATCH 不覆盖终态 | 工具执行中发新消息，旧卡、新卡、实际执行分别核对 |
| 授权交互 | 单击执行一次；并发重复提交、超时、无效 token、提交失败；答题期间 PATCH 不清空输入 | 飞书单击可继续执行；重复点击无重复工具调用 |
| 流式与空卡 | 首事件缺失、工具先到、长静默、PATCH 失败、terminal drain、恢复与乱序 | 长工具任务至少有可见状态，最终正文与结果一致 |
| Topic 与命令 | 普通对话、/compress、/sethome、/restart 的 reply anchor/metadata、原生 fallback | 在真实 Topic 检查每条反馈的位置及消息数量 |
| 发布与安装产物 | 完整 CI、版本一致、wheel/sdist、checksum 与公开 tag 来源 | 从公开安装入口安装，核实 SHA、包路径、sidecar 和 Gateway 请求 |

新增或修改高风险行为的 PR 必须列出本表涉及的行、测试命令及结果、真实验证状态和未覆盖边界。未运行填“未运行”，不能填“通过”。

## 本地与 CI

先按维护指南跑相关模块，再执行 `python -m pytest -q` 和 `git diff --check`。
全量依赖的固定 Hermes 源码通过 `HFC_FIXED_TAG_SOURCE_ROOT` 提供，内容必须通过现有 SHA256 校验；不可指向任意本机生产源码充数。CI 的各平台/SDK/安装器门禁仍然必需。

人工验收遵循 [飞书验收](feishu-acceptance.md)，发布遵循 [发布手册](release-playbook.md)。真实边界缺失时可以交付候选修复，但不能宣称已完成生产修复或关闭未验证的用户问题。
