# 功能准入与体验规则

适用于新增功能、默认值变化和交互重做。[V5 路线建议](../roadmap-v5.md)的核心体验已进入开发分支，当前边界见[任务卡片](../task-cards.md)。本页定义评审与验收方式，不自动授权任何候选功能。

## 产品边界

HFC 把 Hermes 已经发生或已授权的任务过程变成可读、可操作、可恢复展示的飞书/Lark 卡片。执行、会话续跑、模型/工具权限仍归 Hermes。新功能必须首先说明为何原生能力或现有 HFC 功能不能满足需求。

拒绝没有必要的第二套 agent loop、审批队列、通用任务调度器、多平台大一统、独立模型调用或无人值守执行恢复。若必须改变产品边界，先做独立设计评审。

## 每项功能的最小规格

| 字段 | 必须回答 |
| --- | --- |
| 用户与场景 | 谁在什么任务中遇到什么阻碍？issue/观察/反馈在哪里？ |
| 现状与增量 | 现在已经能做什么？新能力具体改变哪一步？ |
| 事实来源 | 哪个 Hermes event/capability 或 Feishu 响应提供数据？未知如何显示？ |
| 状态与身份 | 哪个 profile/bot/chat/thread/sender/turn 可见、可操作？谁拥有状态？ |
| 正常与异常 | 成功、失败、超时、取消、重复、晚到、断线和恢复各发生什么？ |
| 配置与迁移 | 默认、覆盖顺序、显式值、重启、旧配置和回退如何处理？ |
| 成本与边界 | 卡片字节/元素/表格、PATCH 频率、内存、磁盘、权限和依赖成本？ |
| 验收与采用 | 自动化、真实客户端、体验指标、试用反馈和撤回条件是什么？ |

不能回答事实来源、身份或失败路径的功能先做 spike，不直接进入默认路径。

## 用户体验约束

1. **状态说真话。** 区分正在执行、等待输入、最近无新事件、连接待同步、失败/中断和成功；无事件不能证明卡住、结束或后台任务仍活着。
2. **进度必须有依据。** 阶段来自已观测事件；只有可靠的总量/完成量才能显示百分比。`timeout` 不是 ETA，工具最近输出不是实时订阅。
3. **答案与风险范围完整。** 过程可折叠、有界窗口显示，但最终答案和授权范围不能静默截断。溢出要明确提供受支持的完整内容交付方式。
4. **一次操作有可见结果。** 使用原 Hermes resolver，保留幂等回执；过期/旧卡不复活授权。危险动作仍显示完整范围和明确确认。
5. **默认少干扰，细节可到达。** 运行/异常信息优先，成功工具允许折叠。不要增加多个互相冲突的布尔开关；先考虑现有 preset 与有效配置解释。
6. **多端分别验收。** 不凭桌面截图宣称 Android/iOS 通过，不凭缺少可靠客户端标识自动判断“手机模式”。
7. **区分设置与实际运行。** YAML 解析出的下一次配置和进程已经加载的配置必须分开呈现；未知不能显示“已生效”。
8. **数字有明确归属。** 模型、provider、轮次、额度和费用来源必须一致。不能因为本机登录过 GPT/Codex，就在非 GPT 模型卡片显示其周额度；切换模型后的缓存与晚到数据需要隔离。来源不明时隐藏或明确未知，不借用别处的数字。
9. **视觉质量独立验收。** 卡片改版必须覆盖信息层级、字号、留白、颜色、密度、动态稳定性和多端布局。先提供同内容、逐状态的视觉方案确认，再实现；不能以功能测试通过替代真实客户端视觉验收。详见[卡片视觉体验规范](card-visual-guidelines.md)。

## 配置与交互变更

新字段需验证类型、范围、default/global/profile/bot 顺序及显式重置。新安装和已有安装的迁移策略分别写明，已有用户的显式选择优先。写配置的操作必须明确目标作用域、展示差异，具有原子写、备份、失败保持原状及回退路径。

新增按钮/表单复用身份与 transport 认证，不能只凭 message ID、可见卡片或群成员关系授权。只读预览、诊断与实际修改必须有清晰边界；不向群卡片输出私有配置路径、密钥或原始路由标识。

## 持久化与外部投递

新状态需定义 schema、owner、上限、TTL、损坏处理、升级与降级。展示历史默认遵守现有私有检查点边界，不自动演变为永久聊天档案。审批 token、waiter、callback 和执行栈不得持久化为“恢复执行”。

所有组合后卡片使用共享 serializer 审核预算，JSON 1.0 与 2.0 方言各自验证。投递重试必须有已验证的去重标识、结果分类和有限预算；结果未知时不能靠再发一张卡掩盖问题。CardKit streaming 的序号和进程内实体状态不能当成跨重启恢复能力。

## 准入与发布

- 先写当前行为与目标行为，再实现；已有能力只优化体验时，不能包装为全新功能。
- 每个功能至少覆盖一个正常流程、一个失败流程和一个晚到/重复或重启相关边界；具体矩阵以风险为准。
- UX 改动比较基线与候选的真实场景：首屏可操作性、正文完整性、消息数量、操作反馈和多端布局。
- 性能目标先测同硬件/fixture 基线；p95、内存峰值和 PATCH 数不能由单次成功或测试数量推断。
- 默认开启前有小范围试用、明确回退与已记录验收；路线评分不能替代安全与正确性门禁。
